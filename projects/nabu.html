Making NABU's data easier to manage and use

NABU publishes storybooks in children's native languages and reaches more than 12 million learners worldwide. As a product designer, I worked on part of the internal platform their team uses to manage partners and turn data from MySQL, spreadsheets, and Google Analytics into visualizations.

01 Problem

NABU's data lived in a few different places.

Admins needed one place to manage partners, organize that data, and turn it into visualizations.

01

Data was split between MySQL, spreadsheets, and Google Analytics, with no single place for admins to work with it.

02

When a new partner joined, admins set up dashboards by hand and collected data from country managers.

03

Doing that partner by partner took time and made it harder to keep anything consistent.

03 Considerations

Most of the challenge was figuring out how the data should work.

Organizing the data first

Before designing the visualization flow, I spent time understanding how NABU's data was organized and how an admin would need to move through it.

Designing around tables

A lot of this product is tables rather than typical consumer UI, so I had to know which fields mattered to an admin before deciding how a row should be laid out.

Three months to production

We had one semester to design and ship, so we focused on the workflows NABU needed most instead of trying to solve everything.

04 Design system

NABU's system came with the project. We added what the platform needed.

NABU gave us colors, typography, and branding guidelines, so I didn't build the system from scratch. What we added were the table, form, and button patterns the platform needed, which kept more of our time on the data and workflow problems.

05 Final product

A lot of this project came down to tables: how much to put in a row, and what happens when there are two hundred of them.

These are the three decisions I'd talk through first. The screens are unframed so the tables are actually readable.

01 Decision 01

Put the assigned visualizations inside the table row

A role decides which data a partner can see, so the table doesn’t help much if you can’t tell what each role gives access to. There are 200 roles, and the descriptions run long.

A dropdown inside the row expands the assigned visualizations, so several can be read without widening the table
Edit and delete sit at the end of each row, next to Create New Role above the table
Search and pagination bracket the table, since scanning all 200 was never realistic
Trade-off An open dropdown covers the rows beneath it, so only one role can be expanded at a time. Comparing two roles side by side came up less often than checking one, so we kept it.
02 Decision 02

Kept adding a partner in a modal instead of a separate page

Partner requests used to be handled one at a time in different places. Putting them in one table only helps if acting on one doesn’t send the admin off somewhere else.

The modal shows the roles that already exist, so nobody has to open another tab to look them up
Multi-select lets an admin approve or reject several requests at once
Search finds one requester in a longer list
03 Decision 03

Made a role the single place access is decided

Creating a role means naming it, describing it, and picking the visualizations it can reach. That chain is the whole access model: the role decides the assigned visualizations, and those decide what a partner sees. It made sense to keep all of it in one form.

Creating, editing, and deleting all happen where the roles are listed
An admin can give a partner what they need without exposing the rest of the data
Workflow — visualization builder

Nobody has to rebuild a dashboard for every partner.

The final steps let admins narrow the data they need, then preview the visualization before publishing.

06 Takeaways

Where it landed, and what it changed about how I design.

Where it landed

The part of the platform we designed put four jobs in one place: approving partners, managing roles and what each one can reach, organizing the data behind them, and building the visualizations NABU shares. I don't have usage data from after handoff, so I can't say how their week looks now.

What changed how I design
I couldn't organize the interface until I understood how the data itself was organized: what the fields meant and how an admin moved through them.
Working on an internal tool changed what I pay attention to. A search field and bulk actions aren't much to look at, but they take repetitive work out of something admins do every day.
