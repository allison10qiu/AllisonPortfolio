Audit

Three workflows, 41 configuration routes

Different people needed different things from the same configuration, and whatever read-only looked like had to work for all three across every route in scope.

Auditors

Review exactly what is configured, so the current state has to be unmistakable.

Support engineers

Investigate why something isn’t working, so useful information can’t disappear just because it isn’t editable.

Platform engineers

Move between reviewing settings and changing them, so the boundary between the two has to be clear.

I went through all 41 routes looking at how editing worked: recurring controls, dependencies, empty states, and descriptions. The same questions kept coming up on very different screens, which pushed me toward shared read-only behaviors instead of solving each screen separately.

Research

Read-only still needed context

Our team researched what people still needed from configurations they couldn’t change, with more than 10 internal and external participants. I helped prepare the questions, co-facilitated sessions, and synthesized the findings.

Current values weren’t always enough

Showing only the saved value made unfamiliar settings hard to interpret without the surrounding context.

Descriptions still mattered

Removing helper text made some read-only states cleaner, but harder to understand.

Dependencies had to stay visible

Relationships between settings explained why a configuration looked the way it did.

The question changed

I started out asking “What can I remove?” and ended up asking “What context does someone need to understand this without editing it?”

Explorations

Finding how much context to keep

Three early directions each fixed part of the problem and exposed another, which narrowed down what I was actually trying to answer: how much context should stay visible when someone can’t make changes?

Disabled controls

Kept the editable layout, but made the interface feel unavailable rather than intentionally read-only.

Current values only

Made the state clear, but removed context people sometimes needed.

Full configuration

Kept the context, but didn’t separate reviewing from editing enough.

Testing how much context to keep

I tested two read-only designs with Terraform users because I wanted to see how much context they needed to understand a setting they couldn’t change. Version M made the saved value easier to find, while Version H kept descriptions and related settings visible, which helped people make sense of unfamiliar options.

Key decisions

Combining what worked from both

I used the testing findings to explore a combined direction that pulled from M and H. It stayed an exploration and wasn’t released during my internship.

0104
0203
  1. Make the current state visually dominant. The saved framework gets a check and full weight.
  2. Keep descriptions when they add useful context. Execution mode keeps its explanation and link.
  3. Preserve relationships between dependent settings. Runtime version still says it follows the Sentinel framework above.
  4. Make the boundary between viewing and editing explicit. Checks and crosses replace radios and checkboxes, so nothing looks clickable.
01

Selected values carry the weight

Showing only the saved value made some settings harder to interpret, but showing every option at equal weight buried the current configuration. The selected value became the strongest anchor, and unselected options stayed in the background when they explained the range.

That meant giving up a shorter values-only summary, so the read-only page stays closer to the length of the editable one.

02

Dependent settings stay attached to what controls them

Some values only make sense because of a setting above them, and without that link the page was accurate but hard to follow. I kept dependent settings grouped under the setting that drives them, so a reviewer can see why a value exists.

03

Descriptions stay when they answer a question

I didn’t want every description to survive just because it was on the editable page. I kept one when the setting was unfamiliar or the value couldn’t explain itself, and removed it when the value already said enough.

04

A clear way from viewing to editing

For people who can make changes, I explored how the same page moves between reviewing and editing, so editing is always a deliberate step: view what’s configured, enter an editable state, then return to read-only after saving.

System

Turning decisions into component rules

Once the interaction direction was clearer, I applied the same behavior to the nine recurring component types from the audit. Each one got a defined read-only state, plus an empty state where it needed one.

  1. Current state first. Someone should be able to tell what is configured without hunting.
  2. Relationships stay intact. Read-only shouldn’t hide why settings depend on one another.
  3. Context earns its place. Descriptions and alternatives stay when they explain the current state.
  4. Context without competition. Supporting information stays available without competing with the current state.
  5. Editing is intentional. Viewing and changing configuration should feel like distinct modes.

Outcome

From individual screens to reusable behavior

The audit started with individual configuration pages, but the same questions came up across the nine recurring component types. By handoff, I had defined how those components could show the saved state and retain the context someone needed to understand it. The combined design remained an exploration during my internship, and the component rules gave the team a way to carry the work forward.

What I took from the project

I started the audit asking what I could remove from an editable page, but testing two directions made me pay more attention to what people looked for when a setting was unfamiliar. Some needed only the saved value, while others needed a description or a related setting to understand why it looked the way it did. That distinction shaped the combined direction I explored and the component rules I handed off, which gave the team a way to apply the same thinking beyond the pages I worked on.
